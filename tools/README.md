# Validation locale

Configurer `Directory.Build.targets` à partir de l'exemple à la racine, avec `DvInstallDir` pointant vers le jeu installé et les chemins `ReferencePath` appropriés. Ce fichier contient des chemins propres à la machine et reste ignoré par Git.

Exécuter depuis la racine, sous Windows avec le SDK .NET et .NET Framework 4.8 :

```powershell
powershell -NoProfile -File tools/Validate.ps1
```

Le script compile les deux assemblies de scripts Unity à partir des sources présentes, le mod et le programme de tests. Il s'arrête au premier échec. Les tests utilisent les sources réelles de sérialisation, LiteNetLib 1.3.1 et les structs de l'assembly Unity du jeu ; seul le logger du mod est remplacé. Aucun moteur Unity n'est lancé.

`SkipMultiplayerPostBuild=true` désactive la génération documentaire, le packaging et la copie dans le jeu pour cette validation. Un build normal conserve le comportement précédent. Les assemblies de scripts produites dans `build` servent à la compilation : le script ne génère pas `multiplayer.assetbundle` et ne produit donc pas un package jouable complet. Utiliser le workflow Unity du README principal pour les assets de distribution.

Couverture initiale : aller-retour raw/compressed et valeurs d'items, rejet atomique d'un batch tronqué, compteurs invalides, données compressées corrompues, limite de décompression, exclusion de la capacité inutilisée du writer, propagation des erreurs de sérialisation.

Deuxième lot : aller-retour d'une mise à jour de position seule, policy serveur de possession et de distance, identité du demandeur, drops/throws, validation de la cible d'attachement, flags invalides, interactions sur objets non possédés et identifiants joueurs de 0 à 255. Total : 17 tests. Les tests de policy fournissent les faits serveur en entrée ; ils ne simulent pas la physique Unity, la queue de réception ou le rendu des objets tenus.

Le format d'une mise à jour de position seule inclut désormais le flag ItemState déjà compris par l'ancien lecteur. Les messages contenant déjà ItemState gardent leur format. L'objet source n'est pas modifié lors de la sérialisation.

Troisième lot : validation de panier et RPC de quote. Le serveur prend prix et stock depuis son catalogue, vérifie le magasin et la portée, et répond avec un statut, le total et la ligne refusée. Huit tests supplémentaires couvrent prix/fonds, structure, quantités/doublons, disponibilité, données numériques invalides, absence de mutation et aller-retour réseau de la demande/réponse. Total : 25 tests.

Le bouton des caisses shop utilise RequestShopPurchase pour le host et les clients. La transaction revalide prix, stock et shared wallet, puis crée les objets côté serveur ; le flux général items les diffuse. Un timeout ou OperationInProgress conserve le même OperationId pour un retry, et le panier est vidé seulement après un succès autoritaire. Les effets Unity et le receipt restent à tester en session.

À vérifier en jeu pour ce premier lot : départ d'un joueur tenant plusieurs commandes, reprise de ces commandes par un autre joueur, départ pendant interaction aux deux extrémités d'une rame, reconnexion avec réutilisation du PlayerId et RPC avec ping initial nul.
